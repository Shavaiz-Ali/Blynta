# Billing navigation and frontend constants audit

## Delivered behavior

The restored billing header, horizontal summary, subscription card classes, Most Popular badge, upgrade button styles, and One balance section are retained. Credit Management now uses the shared `AppTabs` below those sections. Purchases and history render in the page; `keepMounted` retains history filters and page across tab switches. The existing `#buy-credits` and `#credit-history` links select and scroll to the section without removing Paddle's `_ptxn` query parameter.

Credit History uses real API rows, totals and page counts. Changing a filter resets to page one; selecting the same filter preserves the page. The table uses shared Table, AppSelect, AppBadge and AppPagination controls. Activity is a row feed rather than a literal table: only its reusable container/toolbar/badge classes, centered empty state and skeleton were extracted. Activity retains its category filters, search, domain actions, and pagination scrolling. Its custom pagination markup now delegates to the already-existing Activity variant of AppPagination.

Credit packs retain the existing server-created Paddle transaction flow. Missing configuration disables packs and never supplies a fabricated price. Checkout errors use contextual Sonner retry actions; the permanent Retry checkout link and purchase/history dialog state are removed. The checkout verification and ledger refresh algorithm is unchanged.

Subscription prices and allocations no longer live in the card presentation configuration. The authenticated, read-only `GET /billing/plans` endpoint reads existing configured allocations and actual active monthly Paddle prices. An unavailable price disables that purchase instead of falling back to a hardcoded price. This is the only production backend addition; credit accounting, Free allocation, webhooks, checkout creation, authorization and schemas are unchanged. Deploy this endpoint with/before the frontend.

## Inventory and architecture

Run `node scripts/audit-frontend-constants.cjs` from the repository root. It writes `.test-results/frontend-constants-audit.json`, containing file/line evidence, query-key expressions, native controls, repeated string unions, and resolved import cycles. Generated output, build artifacts, dependencies, scripts and tests are excluded from the authored frontend inventory. Candidate counts are evidence for review, not counts of bugs; route templates, ordinary copy, local state names and SDK protocol values can correctly remain local.

The scan covers 734 files: Main App 275, Admin 136, Auth 79, Studio 142, Web starter 5, api-client 2, auth package 13, types 6, and UI 76. It identifies 151 query-key expressions and these literal candidates:

Shared additions are small domain modules: `packages/types/src/plans.ts` and `identity.ts`, plus typed credit identifiers in `billing.ts`. Billing-only tabs/hashes, endpoints, query keys and filter choices stay in `apps/app/features/billing/constants.ts`. Billing plan icons/classes/copy stay in feature `plans.ts`, and currency formatting in `format.ts`. No giant global constants module was added. Existing serialized identifiers and cache-key arrays are preserved; the plan catalog adds one new key.

The import scan compares the authored graph with HEAD. One existing jobs/dashboard/YouTube barrel cycle remains; zero cycles were introduced. The report lists all members. This checks resolvable source imports, not runtime/dynamic import behavior.

## Shared UI compliance and remaining candidates

Most `components/common` wrappers already re-export `@blynta/ui`, so replacing them would only churn imports. Billing now directly uses the shared tabs, select, cards, table, badges, skeleton/empty presentation, buttons and Activity pagination variant. No custom CSS or custom tab implementation was added.

The scan found nine native controls, including the shared table primitive itself, two hidden file inputs, player volume range, tag editor input, referral-link fields, transcript search and publication search. File/range/tag inputs have specialized behavior and remain appropriate. The referral/search fields are follow-up AppInput candidates; their current compact compound layouts were preserved. NotificationList's custom category tabs are another follow-up candidate requiring separate visual/keyboard checks. The repeated `default|lg|sm` size union belongs to separate AppInput/AppSelect APIs and is not a shared business identifier.

Remaining product-copy review: dashboard UpgradeBanner/UpgradeCard include claims such as HD exports, priority and “10×” credits. They were not silently changed during this billing navigation task. The generic shared AppProductHeader also contains legacy allowance fallbacks; integrating a backend allowance prop across every consuming shell deserves a separate change. These are explicitly deferred audit findings, not claims that every frontend literal has been removed.

The repository BillingPage did not contain the duplicate JSX attributes or repeated CreditPacks/CreditHistory instances visible in the pasted sample. It did contain redundant plan union/order/metadata and obsolete dialog state; those were replaced. The new page renders one instance of each credit view.
